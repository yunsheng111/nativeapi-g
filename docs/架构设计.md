# GLM 中转架构设计

> 项目路径：`D:\GLM2api\relay`（以 glm2api v0.3.0 为底座 fork）
> 设计日期：2026-09-15
> 部署目标：本机 Windows（`127.0.0.1`）

---

## 一、目标与约束

### 需求

| 编号 | 需求 | 归属 |
|---|---|---|
| R1 | 稳定的 API 中转，可在多个客户端调用 | 底座 |
| R2 | 多账号轮换 + 额度池 | 底座 + 加固 |
| R3 | 协议转换后，客户端能正常调用工具 | 协议桥 |
| R4 | 读写本地文件 | 工具运行时 |
| R5 | 执行 shell 命令 | 工具运行时 |
| R6 | 浏览器操作 | 工具运行时 |
| R7 | MCP | 工具运行时 |
| R8 | Skill 技能包 | 工具运行时 |

### 决策

- **工具执行**：两种模式都要，可切换（透传 / 内置）
- **协议覆盖**：OpenAI `tool_calls` + Anthropic `tool_use` 两套
- **部署位置**：本机 Windows，监听 `127.0.0.1`

### 设计约束

1. **不引入重型依赖**：底座是纯标准库，扩展层尽量只用标准库；浏览器/MCP 等确需依赖的模块做成可选安装。
2. **上游可追踪**：`relay/` 保留 git，便于日后 `git pull` 同步上游修复。
3. **失败不可伪装成成功**：工具执行失败必须如实上报，不做静默降级。
4. **安全阀不可绕**：危险命令确认、超时、输出上限、工具白名单。

### 2.2 已修复的底座缺陷

**缺陷：`python -m glm2api` 静默退出，服务不启动。**

- 位置：`src/glm2api/__main__.py`
- 原因：文件定义了 `main()` 但**没有 `if __name__ == "__main__"` 守卫**。`python -m glm2api` 只会导入模块然后退出，exit code 0，零输出。
- 影响面：README 快速开始、Dockerfile 的 `CMD`、Vercel 部署、systemd 单元的 `ExecStart` —— **四处文档写的启动命令全是坏的**。
- 唯一能启动的是项目根的 `main.py`。
- 处置：已补上守卫，并用 `PORT=8011 python -m glm2api` 实测 `/health` 返回 200 确认修复。

## 三、总体架构

### 3.1 双模式

```
                         ┌─────────────────────────────┐
客户端 ── OpenAI/Anthropic ──▶│  中转 (127.0.0.1:8000)      │
                         │                             │
                         │  ┌─ 账号额度池 (100 身份)   │
                         │  ├─ 协议桥 (DSML)           │
                         │  └─ 模式路由                │
                         └───────┬─────────────┬───────┘
                                 │             │
                    模式 A 透传   │             │  模式 B 内置
                                 ▼             ▼
                        客户端自己执行    中转端工具运行时
                        文件/Shell/      ┌─ 文件读写
                        浏览器/MCP/      ├─ Shell (bash/pwsh)
                        Skill            ├─ 浏览器 (CDP)
                                         ├─ MCP client
                                         └─ Skill loader
```

| | 模式 A · 透传 | 模式 B · 内置 |
|---|---|---|
| 工具执行方 | 客户端 | 中转端 |
| 中转职责 | 多账号池 + 协议转换 | 账号池 + 协议转换 + **agent loop** |
| 适用客户端 | Cline / Roo Code / Kilo Code / Continue / Claude Code / Codex CLI | Cherry Studio / LobeChat / Open WebUI 等聊天类 |
| 流转方式 | 工具调用直接下发给客户端，等客户端回传结果 | 中转内部循环：解析 → 执行 → 回灌 → 再问 |
| 改造量 | **小**（现有代码基本可用，需调优） | **大**（工具层需从零用 Python 重写） |

### 3.2 模式选择机制

三层覆盖，优先级从高到低：

1. **请求头** `X-GLM2API-Tool-Mode: passthrough | builtin`（临时覆盖，调试用）
2. **模型名后缀** `glm-4-flash@builtin`（单次请求覆盖，客户端无需改配置）
3. **API Key 绑定**（在管理面板给每个 key 设默认模式，最省事）

默认：`passthrough`（因为透传模式对 agentic 客户端体验最好，且中转无状态）。

### 3.3 模式 B 的 agent loop

```
客户端请求（无 tools）
   │
   ▼
[1] 注入内置工具清单到系统提示词（复用 build_tool_call_instructions）
   │
   ▼
[2] 请求 GLM 网页版 ──────────────────────┐
   │                                       │
   ▼                                       │
[3] 流式解析 DSML                          │
   │                                       │
   ├─ 无工具调用 ──▶ [7] 收尾，返回客户端  │
   │                                       │
   └─ 有工具调用                            │
        │                                  │
        ▼                                  │
   [4] 执行工具（受白名单/安全阀约束）       │
        │                                  │
        ▼                                  │
   [5] 结果序列化为 <|DSML|tool_result>     │
        │                                  │
        ▼                                  │
   [6] 追加到对话历史，回到 [2] ───────────┘
```

**关键设计：流式体验**
模式 B 下中转会长时间无输出（工具执行 + 多轮往返），会撞上客户端 idle timeout。对策：
- 每 5 秒发 SSE 注释 `: keepalive`
- 把**工具执行进度**作为 `content` delta 实时下发，用户能看到「正在读取 src/main.py…」「执行 npm test…」
- 这个进度不是剧透，是可观测性，必须做

```

├── src/glm2api/               # 底座（尽量少改，便于同步上游）

│   ├── server.py              # ← 扩展点：模式路由、/v1/messages
│   └── services/
│       └── glm_auth.py        # ← 扩展点：配额统计、熔断、健康探测

│   ├── __init__.py
│   ├── accounts/              # 账号额度池加固
│   │   ├── pool.py            #   加权轮询 + 失败摘除 + 冷却恢复
│   │   ├── stats.py           #   每账号配额/成功率/最后使用时间
│   │   └── health.py          #   定期健康探测
│   ├── bridge/                # 协议桥
│   │   ├── mode.py            #   模式判定（请求头/模型后缀/API Key）
│   │   ├── openai_bridge.py   #   OpenAI tool_calls 双向转换 + 边界修复
│   │   └── anthropic_bridge.py#   Anthropic tool_use 双向转换
│   ├── agent/                 # 模式 B 的 agent loop
│   │   ├── loop.py            #   多轮循环 + 进度流 + keepalive
│   │   └── session.py         #   会话状态
│   ├── tools/                 # 工具运行时（Python 重写）
│   │   ├── registry.py        #   注册表 + 白名单（物理隔离）
│   │   ├── fs.py              #   read / write / edit / glob / grep / delete
│   │   ├── shell.py           #   bash / pwsh
│   │   ├── todo.py            #   todowrite
│   │   ├── browser.py         #   CDP 接管本机 Edge/Chrome
│   │   ├── mcp.py             #   MCP client
│   │   ├── skills.py          #   SKILL.md 加载器

│
├── docs/                      # 设计文档（本文件所在）
├── tools/                     # 验证与诊断脚本
└── tests/                     # 回归测试
```

**边界原则**：底座代码只做最小改动（打扩展点），新逻辑一律进 `glmrelay`。这样上游更新时冲突面最小。

### P1 的量化目标

| 指标 | 现状 | 目标 |
|---|---|---|

### P2 的边界用例清单

必须逐一验证并加回归测试：

1. 单轮多工具并行调用
2. 工具参数含代码围栏 / JSON 字符串 / 换行
3. 工具参数深嵌套对象与数组
4. 超长参数（>5KB）
5. 同一参数名重复出现
6. 模型把 DSML 写在 `content` 而非被识别（**已实测出现过 1 次**）
7. 推理模型（`-think`）在思考阶段调用工具
8. 客户端回传多段 `role:"tool"` 结果
9. Anthropic 格式下的 `tool_use` / `tool_result` 互转
10. `tool_choice` 三档（none / required / specific）

## 六、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **上游改版打死逆向接口** | 致命 | `tools/verify_base.py` 作为冒烟测试，每次启动前跑；出问题第一时间定位 |
| 上游更新导致底座 diff 冲突 | 中 | 新逻辑隔离在 `glmrelay`，底座只打扩展点 |
| 游客身份被风控 | 高 | device_id 轮换（底座已有）+ 账号池熔断（P1 新增）+ 建议补充真实账号 token |
| 模式 B 长时间无输出触发客户端超时 | 中 | keepalive + 进度流（见 3.3） |
| 内置工具误删用户文件 | **致命** | 工具白名单物理隔离 + 危险命令确认 + 默认只读档 + 路径沙箱 |
| CDP 接管浏览器与用户日常浏览器冲突 | 中 | 使用独立 user-data-dir 启动专用实例，不接管用户正在用的窗口 |
| DSML 协议依赖模型"听话" | 中 | 显式提示词约束 + 解析失败留存样本 + `tool_choice` 强制档 |

### 安全默认值

模式 B 上线时的默认姿态：

- 工具档位默认 **只读**（read / glob / grep），要写要执行需手动提档
- 文件操作限制在配置的项目根目录内，拒绝 `..` 逃逸
- Shell 命令走危险命令正则拦截（参考 glm-web-code 的 `dangerous_cmds.go`）
- 命令超时 30s、沙箱超时 60s、单次输出上限 1MB
- 破坏性操作（删除、格式化）需二次确认
