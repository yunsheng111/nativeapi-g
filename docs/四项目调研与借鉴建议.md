## 摘要

一句话结论：**这四个项目在"账号池调度"与"反检测"上比本项目走得远，但在"协议桥正确性"与"上下文治理"上比本项目更差 —— 而后者恰恰是本项目的核心资产。**

三点最有价值的发现：

1. **上下文长度保护是四个项目的共同缺失，也是本项目的缺失。** 四个仓库全部采用"全量历史压平 → 每轮重传"，无一有截断/摘要/token 上限。本项目 `translator.py:436-459` 同样无保护，`core/tokenizer.py` 的 token 估算只用于 usage 上报，未参与裁剪。**这不再是"别人的缺陷"，而是拍平式协议桥的结构性后果**——与本文档体系 7.5.2 的推导完全一致，只是我们还没补上。**列为 P0。**

2. **本项目对 HTTP 状态码没有分类，导致"暂态错误"与"账号失效"被混为一谈。** `glm_auth.py:373-384` 的 `should_switch_account()` 对**任意**带 `status_code` 的异常一律返回 `True`（切号）；全仓库 **零处** 处理 `Retry-After`。对照：chatgpt2api 把 `404/409/423` 归类为"资源未就绪，继续轮询"（`openai_backend_api.py:1462`），gptGrok2api-B 用中英双语正则解析 `Retry-After`（`pool.go:18`）。**成本极低、收益直接。列为 P0/P1。**

3. **"身份字段单一数据源 + 矛盾自检"是唯一一条我认为应当移植的反检测设计。** 它出自 turb-gpt-free-register（`config/browser.py:355-380`），但其**中性内核是"多传输层状态自洽"，与欺骗检测无关**。本项目当前同时存在 urllib 与 CDP 两条传输（10.8.1 警告的"同设备双指纹"），正需要这个结构。**移植时必须剥离一切"伪装成真人"的意图。列为 P1，与 P2.5 第二批合流。**

**关于自动注册**：四个项目里两个具备完整注册链路、一个曾具备后被作者主动移除（chatgpt2api 的 CHANGELOG 记载"移除注册功能、防滥用机制导致封禁 GitHub 账号"）。本项目定位是**本机自用、以自有账号登录态做协议转换**，已有"一键拉起浏览器登录导入"的人在环路径。**注册自动化、验证码求解、指纹伪装一律不移植**，理由见第七章。

## 三、逐项目拆解

### 3.1 basketikun/chatgpt2api

**核心功能与定位**：把 chatgpt.com 官网私有后端接口（`/backend-api/*`）用**纯协议方式**逆向成 OpenAI + Anthropic 双协议 API，并把"多账号轮询取图"做成可运营号池。**6,335 star 说明它是这个生态里最成熟的一个**——形态与本项目最接近（私有后端 → 标准协议），因此**它的可取之处也最直接适用**。

**架构特点**：

1. **存储后端抽象**：`StorageBackend` ABC 定义 6 个方法，json/sqlite/postgres/git 四实现，环境变量选后端。**对本项目是过度设计**（见第七章），但它证明了一件事：账号池的存储形态是可替换的。
2. **协议层与数据面分离**：`services/protocol/*` 负责各协议适配，`openai_backend_api.py` 负责上游交互，中间有 `conversation.py` 做归一化。本项目 `translator.py` + 三个 adapter 是同构的，只是没分这么细。
3. **反检测是"账号级持久化"而非"全局伪装"**：`_build_fp()` 把 UA / impersonate / `oai-device-id` / `oai-session-id` / `sec-ch-ua*` 绑到账号上，**同号每次复用同一套指纹**（`openai_backend_api.py:239-266`）。这与本项目 D1 的"真实 deid 接线"是**同一个洞察的两个实现**——身份必须稳定，不能轮换。
4. **轮询是它的主形态**：因为 ChatGPT 的图片/文件是"SSE 传事件 + 异步产物"，必须轮询。**GLM 是 SSE 直出结果，本项目不需要**。

**最亮的一条**：**Anthropic XML 工具桥 + 流式截断保护**（`anthropic_v1_messages.py:17-18, 181-184`）。它的 `streamable_text()` 在流式场景下**截断到第一个工具标记之前**，从源头上避免工具标记泄漏给客户端。本项目 P2 用例 #6 正是"DSML 写入 content"，但我们的做法是**事后抢救**（`_repair_corrupted_markup`），它的是**事前截断**。两者是上下游关系，不冲突。

**它自己的硬伤**（本项目不要学）：

- **无上下文长度保护**（`conversation.py:693` 全量直传）。
- **主动不复用会话**：`parent_message_id: new_uuid()`（`openai_backend_api.py:533`）——作者写了上游会话恢复协议的文档（`docs/upstream-sse-conversation.md`），说明**理解**机制但**主动选择不用**。代价是多轮延迟与成本偏高。
- **并发槽位泄漏且不自愈**：`account_service.py:1073-1077` 的 docstring 自己承认"槽位泄漏 → 账号被静默排除出调度，可借此在 UI 上诊断"。**把缺陷当成可观测特性**。
- **中文字符串状态机**：`{"正常","限流","异常","禁用"}` 散落 6+ 处，无枚举约束。
- **退避策略不统一**：三套不同退避（指数/线性/固定）散在三个文件。
- **CI 不跑测试**：36 个测试文件，workflow 只做 Docker 构建发布。
- **挑战无降级**：`if arkose.required: raise RuntimeError(...)` —— 遇到无法求解的挑战即整条链路不可用，没有换号重试也没有明确错误码。

### 3.2 AuuCoder/gptGrok2api（Python 版，fork 上游）

**核心功能与定位**：把 ChatGPT 网页版与 Grok 网页版/Console 的订阅账号批量注册成池，对外提供 OpenAI + Anthropic 兼容 API 的自托管网关。**多上游抽象层**是它的特色：`app/dataplane/reverse/protocol/` 下按上游分文件（`xai_chat.py` / ChatGPT 相关），上层 `app/products/openai/` 做统一出口。

**架构特点**：

1. **控制面 / 数据面分离**：`app/control/`（账号、代理、配置的 CRUD 与持久化）与 `app/dataplane/`（热路径：选号、转发）分开，控制面用 SQLAlchemy/Redis，数据面用**列式数组 + 最小锁**。
2. **热路径锁设计**（`app/dataplane/account/__init__.py:29-38` 类文档）：`_table` 原子替换（读方永不见中间态）；`_lock` 只护表变更；**选号时锁内拷贝候选集、锁外评分、只在 inflight+1 时重新加锁**；增量同步用独立 `_sync_lock` 避免阻塞选号。**这是一个值得学的锁粒度设计。**
3. **双选号策略**：`quota`（评分制，需主动探配额）与 `random`（均匀随机 + 冷却，零探测）两套完全独立的实现，进程级注册一次。**这个"双策略开关"本身就是最值得抄的一点**——因为它是同一个问题的两种答案，而本项目还没回答这个问题。
4. **注册链路的精髓是"浏览器状态回流"**：真实浏览器过完验证码后，把 cookie/localStorage/React state **全量导回纯协议 session**（`services/register/grok_protocol.py:1403-1457`），让后续 HTTP 请求保持同一浏览器身份。**这与本项目 importer 的思路同构**（浏览器登录 → 抓凭据 → 纯协议复用），P2.5 第二批的 BrowserContext 池是它的延伸。

**最亮的一条**：**健康度乘性衰减 + 状态码差异化因子**（`app/dataplane/account/feedback.py:17-24, 81-93`）：成功 `+0.12`；`401 ×0.55 / 403 ×0.25 / 429 ×0.45 / 5xx ×0.75`，下限 0.05 上限 1.0。**用衰减力度区分"账号问题"与"上游抖动"**——5 个常量 + 2 个函数，移植成本极低。

**它自己的硬伤**：

- **代理选号只看 inflight**（`app/dataplane/proxy/selector.py:28-34`）：`min(healthy, key=lambda n: n.inflight)` 完全不看历史失败率、延迟、是否刚被 CF challenge。**B 的做法明显更好。**
- **重试上限被策略劫持**（`app/products/_account_selection.py:12-24`）：random 策略下硬编码返回 5，配置文件的 `retry.max_retries` 被静默忽略。
- **魔法值硬编码**：`Authorization: Bearer anonymous`（`headers.py:340`）、`_statsig_id()` 的固定 base64 回退值（`headers.py:77-80`）。**抓包抄来的魔法值一旦被上游标记，全量失效且无降级。**
- **打码与注册内置主仓库**：上游任何一道盾升级都会让主仓库 build/运行失败，且 issue 里已出现"注册失败 HTTP 403"。

### 3.3 lichao199208/gptGrok2api（Go 重写版）

**核心功能与定位**：同 A 的功能面，但整体重写为 Go，并把注册能力**拆成外部 HTTP driver**（`RegisterMailURL` / `RegisterCaptchaURL` / `RegisterDriverURL` 三个外部服务）。**这是一个更可维护的方向——代价是失去护城河。**

**架构特点**：

1. **账号池的核心是"零探测下的稳态吞吐"**：只靠 inflight 计数 + 冷却时间 + 容量排队，**永不主动打上游探配额**。代价是无法回答"这个号还能用几次"，只能等 429 才知道。**与 A 的 quota 策略是同一问题的另一种答案。**
2. **并发上限用"等待而不是拒绝"**（`internal/accounts/pool.go:117-128`）：全部账号达上限时不返回错误，而是阻塞在 broadcast channel 上等别人释放，用调用方 `ctx` 超时兜底。`signalLocked()` 用 `close(p.wake); p.wake = make(chan struct{})` 做广播唤醒。**"宁可排队也不 429"的取舍。**
3. **copy-on-write + 写合并**：`AccountSnapshot()` 返回不可变视图，调用方不得修改；`scheduleAccountFlushLocked` 用 1 秒定时器合并落盘 + revision 比对跳过无效写（`internal/store/json.go:439-459, 541-578`）。
4. **`looksRecovered()` 恢复判定**（`pool.go:295-316`）：状态写着"异常"，但配额回来 + `survival_alive=true` + 无残留错误标记 → 允许重新参与选号。**解决"账号被误判异常后永久沉底"。**

**最亮的一条**：**代理节点"稳定/探针"分层 + canary + 物理淘汰**（`internal/proxy/transport.go:170-177, 429-470, 617-680`）：连续成功 3 次升为稳定节点（主力走它），**每 20 次选号放一次 canary 到未验证节点**，连续失败 3 次物理移除。

> **为什么这条对本项目重要**：本项目没有代理池，但有**两条传输通道**（urllib / CDP fetch），且 P2.5 第二批计划做 canary A/B 分流。**B 的调度策略可以原样迁移到传输通道维度**——"主力走已证明的通道，按比例放 canary 验证另一条，连败 N 次淘汰"。这是本次调研里**映射得最漂亮的一条**。

**它自己的硬伤**：

- **`ExtractMessage` 丢弃 `tool_calls` 与 `role=tool`**（`internal/protocol/chat.go:66-78`）：只取 `contentText(message.Content)`。**这会直接破坏 Cline / Claude Code 类依赖工具结果回灌的客户端。** 本项目恰好以"工具桥正确性"为核心资产，这类退化是明确的反面教材。
- **Grok 路径无指纹伪装**（`internal/provider/grok_chat.go:78`）：硬编码 Linux UA、无 client hints、无 `Sec-Fetch-*`、走标准库 `http.Client`（无 TLS 伪装）。**对照 A 的 11 个头 + 动态 statsig，这个伪装强度接近裸奔。**
- **`registerEvents` 用 1 秒 ticker 做 SSE**（`internal/httpapi/register.go:648`）：对"事件驱动"的宣称不诚实。
- **仓库卫生**：遗留 `DIFF_FILE.txt`、`README.md.orig`、`VERIFICATION.txt`、`ROLLBACK.sh`、10 个 `scripts/inspect_*.sh`。文档质量直接受影响。
- **无上下文长度保护**（与 A 共同硬伤）。

### 3.4 myfanhua/turb-gpt-free-register

**核心功能与定位**：批量生产 ChatGPT 免费账号、并自动加工成 Codex/CPA 凭证**推送给下游中转服务**的凭证供应商。**它不是中转服务，与本项目不是同一物种。**

**架构特点**：

1. **五套浏览器驱动可选**：protocol（纯 HTTP 13 步）/ roxy-Selenium / cloak-Playwright / browser_use / skyvern，由配置切换。**驱动的可替换性是它的架构核心。**
2. **邮箱池九源按序兜底**：主力是外购 Outlook 账号池（Graph + IMAP 双协议取信）。
3. **验证码不接打码平台，而是把官方 `sdk.js` 放进 Node `vm` 沙箱伪造环境让它自己算**（`core/sentinel_runner.py` + `sentinel/sdk.js` 30,863 字节混淆文件）。
4. **配置模块膨胀到 17 个**（`config/browser.py` / `humanize.py` / `proxy.py` / …），指纹画像集中在一处供三层共用。

**最亮的一条**：**指纹单一数据源 + 跨三层矛盾自检**（`config/browser.py:1-12, 355-380`）。同一 BrowserSession 内，**curl_cffi 的 TLS/HTTP 头、Python 端生成的 Sentinel `p` 数组、Node VM 里的 `sdk.js` 环境**共用同一个画像 dict；`validate_browser_profile()` 返回矛盾点列表并打 warning（UA 与 `chrome_full_version` 不一致、macOS 画像但 UA 不是 Macintosh、`navigator.language` 不在 `navigator.languages` 中……）。

> **为什么这条对本项目重要**：它的**中性内核是"多传输层身份字段必须自洽"**——绝大多数被识别不是因为某个字段假，而是因为**多个字段互相矛盾**（TLS 146 配 UA 149、时区东京配语言 zh-CN）。本项目同时存在 urllib 与 CDP 两条传输，F4 记录的"UA 自称 Edge 143 + Python OpenSSL + HTTP/1.1"正是**同一类矛盾的现成实例**。**移植时必须剥离"伪装成真人"的意图，只保留"状态自洽"这个工程内核**（见第七章）。

**它自己的硬伤与风险**（本项目明确不学）：

- **单进程锁的架构上限**：账号领取靠 `threading.RLock` + 整表读改写（`core/db.py:2331-2342`），每次领取反序列化整表，无法多进程扩展（README 自认）。反例参考：应用 `UPDATE ... WHERE status='available' LIMIT 1` + `BEGIN IMMEDIATE`。
- **依赖大量外部商业服务**：RoxyBrowser、CloakBrowser、Browser Use Cloud、Skyvern、GrizzlySMS、Remail、MailNest、GPTMail…… 任一家停服即打断主流程。
- **仓库卫生与 README 不符**：README 声称"真实数据均已排除"，但仓库里**直接提交了** 3.9 MB 真实抓包 HAR、含生产 `oai-device-id` 的 `are-capture-*.jsonl`。**教训：`.gitignore` 排除运行时数据是必要但不充分的——抓包产物往往绕过规则。**
- **零合规声明**：1,341 star 的项目，全仓库无任何免责声明。
- **默认值不一致**：`config/browser.py:76` 设 `REJECT_CLOUD_PROXY = False`，但 `core/session.py:287` 读取时 `getattr(..., "REJECT_CLOUD_PROXY", True)` —— 配置加载失败会静默变成"拒绝云厂商"。

## 五、对照本项目的差距分析

逐维度对照当前代码实测（非文档描述）后的差距：

### 5.1 账号池管理

**已有**：`token.txt` + `accounts.json`（原子写、按指纹去重）、轮询/failover 选号、连续 3 次失败熔断 600s + 半开、风控冷却（3 次风控事件 → 10 分钟）、300s 逐账号探活、单身份单飞（`glm_client.py:138` 的 `_account_locks` 互斥锁数组）、请求抖动 200ms、游客错峰 5s、`AccountState` 统计字段（`glm_auth.py:55-73`）。

**差距**：

| 差距 | 对照做法 | 影响 |
|---|---|---|
| 健康度是**离散三态**（正常/熔断/冷却），无连续权重 | gptGrok A 的乘性衰减因子 | 403 与 5xx 被同等对待；"连续 3 次失败才摘"比"立即降权"晚止损 |
| **无"新账号宽限"**：刚导入账号首次失败即计入熔断计数 | chatgpt2api 的 10 分钟宽限 + `invalid_count<=1` 暂缓 | 号是稀缺资产；导入后立即遇网络抖动可能被误摘 |
| **无账号级 inflight 计数**（互斥锁 = 并发 1） | chatgpt2api 的 `image_account_concurrency` 默认 3 + Condition 排队 | 这是 D3 的有意取舍（风控优先），**不宜直接改**；但缺"可配置放宽"的出口 |
| 运行统计**纯内存态**，重启即丢（`_persist_refresh_token` 只落 token） | gptGrok B 的写合并持久化 | 影响可观测性连续性，不影响正确性；**优先级低** |
| **无配额感知** | chatgpt2api 从上游 `limits_progress` 拉 `remaining` | GLM 是否有等价字段未知 → 列为观察项 |

> **关于"写合并 debounce"**：本项目账号池的落盘是**事件驱动**的（导入/删除/refresh_token 变更），不是每请求写盘，因此 gptGrok B 的 debounce 设计**对本项目不适用**。已核实 `store.py:188` 走"临时文件 + `os.replace`"原子写，当前形态健康。

### 5.2 API 转换与转发

**已有（这是本项目的核心资产，四个项目里无人可比）**：DSML 提示词驱动协议、OpenAI `tool_calls` + Anthropic `tool_use` 双协议实测全通、畸形标记抢救层（两族实测样本）、工具结果体积治理（24000 字符首尾保留）、不可信输入信任壳、`tool_call_id` 对齐显式报错、黑名单按名字+来源匹配。

**差距**：

| 差距 | 对照做法 | 影响 |
|---|---|---|
| 抢救层是**事后修复**，缺**事前截断**防线 | chatgpt2api `streamable_text()` 截断到首个工具标记前 | 标记已进 content 才抢救，模型已"看见"污染 |
| 工具强制语强度未对齐 | gptGrok A `tool_prompt.py:46-49`：`tool_choice=required` 时写 `Do NOT write any plain-text reply under any circumstances` | 本项目工具桥成功率有波动（12.6/12.8 记录 5/6），服从率是已知瓶颈 |
| 自注入内容（信任壳声明）**是否逐轮累积**未核实 | gptGrok A 把上一轮自己注入的 `## Sources` 段正则剥掉再压平（`chat.py:288-300`） | 若累积，长对话必然膨胀 → 与 5.5 的上下文问题叠加 |

### 5.3 自动注册流程

**已有**：一键拉起独立浏览器 → 轮询 localStorage → 自动抓 `refresh_token` + `chatglm-deid` → 可连续换号；粘贴兜底识别四种格式。

**差距**：仅一处值得补 —— **轮询缺 settle 稳定窗口**。turb-register 的 `core/outlook_client.py:1072-1099` 在拿到第一个候选后**继续等 N 秒看是否有更新的**，避免抓到"半成品"（token 尚未写完）。本项目 importer 是"抓到即返回"，**存在抓到半截凭据的理论风险**。这是纯正确性修正，成本约 20 行。

**其余注册相关能力一律不移植**，理由见第七章。

### 5.4 反检测与限流

**已有**：真实 deid 接线（废除 8 次轮换）、去掉 XFF 伪造、并发 6 + 单身份单飞 + 抖动 + 错峰、风控事件分类与冷却、CDP 真实浏览器指纹（TLS/JA4/HTTP2/头序天然正确）、传输级熔断回落、禁止头剔除（少伪装 = 少被识别）。

**差距**（本节差距密度最高）：

| 差距 | 对照做法 | 影响 |
|---|---|---|
| **对 HTTP 状态码无分类**：`should_switch_account()`（`glm_auth.py:373-384`）对**任意** `status_code` 一律切号 | chatgpt2api 把 `404/409/423` 归为暂态继续等；gptGrok A 的 `classify_status_code()` | **404（资源未就绪）会误判为账号失效而切号**，浪费账号且掩盖真实原因 |
| **全仓库零处处理 `Retry-After`**（grep 实证） | chatgpt2api / gptGrok B 均尊重 `Retry-After`；B 还支持中英双语 | 上游明确告知"请等 N 秒"时，本项目按自己的指数退避走 → 可能过早重试 |
| urllib 路径**指纹自相矛盾**（F4：UA 自称 Edge 143 + Python OpenSSL + HTTP/1.1） | turb-register 的画像矛盾自检 | 已是挂账项；缺一个**可回归的自检**把它固定住 |
| **无全局最小间隔节流**：并发闸门 + 随机抖动，但抖动不保证最小间隔（6 线程可能同时醒来） | turb-register `plan_check_service.py:41-55`（单调时钟 + min_interval + jitter 分配"下一个请求时刻"） | 瞬时并发峰值仍可能高于预期 |
| 403 触发浏览器自愈时**是否惊群**未核实 | gptGrok A：403 只打标记，下次请求前锁内双重检查后重建 | 多并发同时重建浏览器会放大故障 |
| 传输回落时**是否保留会话状态**未核实 | turb-register：重试只清熔断、**保留 Cookie Jar**（`openai_auth.py:246-253`） | 回落 urllib 重放时若丢 cookie，会二次触发风控 |

### 5.5 上下文管理

**这是本次调研最重要的自省。**

四个项目**全部**没有上下文长度保护。本项目**同样没有**：`translator.py:436-459` 把整段对话拍平成一条 user 文本，无截断、无摘要、无 token 上限；`core/tokenizer.py` 的估算函数**只被 `translator.py:13` 用于 completion tokens 上报**，未参与裁剪。

**为什么这是结构性的，而不是四个作者都疏忽**：

拍平式协议桥把"多轮消息"压成"一条 user 纯文本"，通道只运文本、语义由提示词供给（本项目文档 7.5.1 的结论）。**代价必然转移到体积上**——一次 `fetch` 抓回的整页 HTML 会被原样塞进那条唯一的 user 消息，三个上限依次撞上（上游单条消息长度 / 模型上下文窗口 / 推理时长与风控触发概率）。**这是纯接口方案的内生需求，不是从快照派借来的设计知识。**

**本项目相对四个项目的一处领先**：已有**工具结果**体积治理（`GLM_TOOL_RESULT_MAX_CHARS=24000`，首尾保留 75%/25%，附"请分页抓取或先摘要"指引）。但**用户历史消息无任何治理** —— 保护只覆盖了回灌路径，没覆盖对话路径。

**另一处差距**：`conversation_id` 恒为空 + 用后即删（`glm_client.py:430, 523`）。chatgpt2api **主动不复用**（`parent_message_id: new_uuid()`），并在文档里写明自己理解会话恢复协议。本项目应**评估 GLM 是否支持会话续接**——若支持，多轮 + 附件场景的收益很大（附件不必每轮重传）。

### 5.6 API 轮询

**本项目不需要任务轮询**：GLM 的 chat 是 SSE 直出结果，与 gptGrok2api 的 Grok 侧同构（"Grok 不需要轮询，ChatGPT 需要"——差异来自上游架构，不是设计优劣）。现有的"轮询"只有 300s 账号探活。

**可迁移的三条**：

1. **`retry_after=0` 特判 + sleep 裁剪到剩余预算** → 本项目 `next_risk_backoff()`（`glm_auth.py:520`）应确认不退避超预算。
2. **`404/409/423` 归类为暂态** → 见 5.4 的状态码分类。
3. **settle 稳定窗口 + 超时降级返回候选** → 见 5.3 的 importer。

## 七、明确不采纳清单

### 7.1 合规红线（不做，且不做理由说明）

| 不采纳项 | 出处 | 理由 |
|---|---|---|
| **全部自动注册链路** | gptGrok A `services/register/`、turb-register 全部 | 批量创建账号违反上游 ToS；本项目定位是**本机自用、以自有账号登录态做协议转换**，与"批量生产 + 转卖凭证"性质完全不同。**本项目已有的人在环登录导入（importer）是正确路径，不需要替换。** |
| **验证码/挑战求解** | chatgpt2api `utils/pow.py`、`utils/turnstile.py`、gptGrok A `captcha-solver/`、turb-register `core/sentinel.py` + `sentinel/sdk.js` | 规避技术保护措施。turb-register 把官方 `sdk.js` 放进 Node 沙箱伪造环境执行，性质等同于"提供专门用于规避技术措施的装置"。 |
| **指纹伪装（伪装成真人）** | turb-register `config/browser.py` 画像池、`core/roxy_registration.py:212-238` 的 webdriver 抹除脚本 | 唯一用途是让自动化流量不被识别为自动化。**注意区分**：P1-2 移植的是同一文件里"状态自洽"的**自检结构**，不是"伪装"的意图。 |
| **外购邮箱池 / 接码平台** | turb-register 的 Outlook 池（含 `clientId + refreshToken`）、GrizzlySMS | 邮箱素材来自第三方批量账号交易；接码用于绕过手机验证。 |
| **代理池** | gptGrok A/B、chatgpt2api、turb-register | 本项目是本机直连（`127.0.0.1`），无此需求。**但 B 的 canary 调度策略可迁到传输通道维度（P1-1），这是思路迁移不是代理池移植。** |

> **一句话边界**：本项目的反检测目标是**"让自有账号的正常使用不被误判"**，不是**"让批量自动化不被发现"**。前者是稳定性工程，后者是规避。四项目里有价值的部分（状态自洽、退避、冷却、分类）全部属于前者。

### 7.2 移植时的方法论边界

P1-2 是本清单里唯一一条"来自反检测模块"的建议。移植它时必须做三件事：

1. **只取结构**：保留"单一数据源 + 矛盾点枚举 + warning 日志"，删除画像池随机化、GeoIP 驱动的语言/时区对齐等**伪装意图**部分。
2. **只做自检不做伪造**：`validate_identity()` 的产出是**日志与告警**，不是"自动修正成更像真人"。
3. **明写用途**：注释里写明该模块服务于"urllib 与 CDP 双传输的身份一致性"，与本项目既有的"少伪装 = 少被识别"（11.3）同源。

### 7.3 架构不匹配（直接搬会坏）

| 不采纳项 | 出处 | 理由 |
|---|---|---|
| **多存储后端抽象 + 工厂** | chatgpt2api 四后端；gptGrok A 四后端（2,200+ 行） | 对"监听本机的单进程服务"是纯过度设计。本项目纯标准库，引入 SQLAlchemy/asyncpg/aiomysql 只为"以后可能换库"不成立。 |
| **curl_cffi / tls-client 做 TLS 伪装** | chatgpt2api、gptGrok A/B、turb-register | 本项目**已有 CDP 真实浏览器**，TLS/JA4/HTTP2 指纹天然正确。这一层应跳过，需要伪装时从 CDP 层做（`Page.setUserAgent` 等）。 |
| **FlareSolverr 等外部容器** | chatgpt2api `docker-compose.warp.yml` | 引入 4 个额外容器与"单机单进程"定位冲突；CDP 层本身能过 CF 挑战。 |
| **中文字符串状态机** | chatgpt2api（`"正常"/"限流"/"异常"/"禁用"` 散落 6+ 处） | 反面教材：无枚举约束，拼错不报错。本项目若扩展状态字段，用 `enum.Enum`。 |
| **JSON 全量覆写存储** | chatgpt2api `json_storage.py:29-43` | 每次改一个账号即全量序列化写盘，号池上百即卡。本项目 `accounts.json` 是事件驱动写，当前健康；若扩容则用 JSONL 追加或 `sqlite3`。 |
| **写合并 debounce** | gptGrok B `json.go:541-578` | **对本项目不适用**：账号池落盘是事件驱动（导入/删除/token 变更），不是每请求写盘。已核实 `store.py:188` 原子写形态健康。 |
| **多副本并发槽** | chatgpt2api `threading.Lock` + 内存态 inflight | 本项目明确"单进程、监听本机"，当前适用。但**需在文档里写下"不支持多副本"的约束**，否则是隐形地雷。 |
| **`ExtractMessage` 丢弃 tool_calls** | gptGrok B `internal/protocol/chat.go:66-78` | 会破坏 Cline / Claude Code 类客户端。本项目以工具桥正确性为核心资产，这是明确反面教材。 |
| **1 秒 ticker 冒充 SSE** | gptGrok B `internal/httpapi/register.go:648` | 对"事件驱动"的宣称不诚实，且每连接固定 1 次/秒序列化成本。 |
| **魔法值硬编码无降级** | gptGrok A `headers.py:340`（`Bearer anonymous`）、`:77-80`（固定 base64） | 抓包抄来的值一旦被上游标记即全量失效。本项目若引入此类值，必须集中在端点表 + 显著注释 + 降级路径。 |
| **挑战无降级路径** | chatgpt2api `openai_backend_api.py:2679-2680`（arkose 直接 `raise`） | 本项目应保证：无法处理的挑战 → 换号重试或返回明确错误码，而不是 500。 |

### 7.4 仓库卫生（从四项目反面教训中提炼，本项目适用）

## 八、未验证项与存疑点（诚实清单）

**调研方法限制**：
